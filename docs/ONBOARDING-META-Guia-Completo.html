§1.1 · P0 imediato — rotação das credenciais expostas FAZER HOJE

  • business.facebook.com → Configurações do negócio → Usuários → Usuários do sistema: selecionar o System User → Gerar novo token (mesmos escopos: whatsapp_business_messaging, whatsapp_business_management) → copiar.
  • developers.facebook.com → seu app → Configurações do app → Básico: em Chave secreta do app, clicar Redefinir → copiar a nova.
  • Atualizar WHATSAPP_CLOUD_TOKEN e WHATSAPP_APP_SECRET na Vercel (web) e na Railway (worker) → redeploy dos dois.
  • Revogar o token antigo (ao gerar novo token de System User o anterior continua válido — revogue na lista de tokens do System User). A redefinição do App Secret invalida o antigo sozinha.
  • Smoke test: enviar 1 mensagem via curl com o token novo e mandar 1 inbound para validar a assinatura nova do webhook. envio 200 OK + inbound processado no log após a troca.
Por que isso vem antes de tudo A verificação e o review chamam atenção humana da Meta para o app. Credencial vazada + app sob análise é o pior momento possível para um incidente. 15 minutos de trabalho, risco eliminado.

§2 · FASE 1 — Verificação do negócio GATE MESTRE

É o pré-requisito de tudo: App Review exige portfólio verificado, o selo destrava o limite de 200 clientes/7 dias e remove o teto de 250 conversas/dia iniciadas pelo negócio. Leva de 10 minutos a 5 dias úteis (mediana: ~2).

Antes de submeter — dossiê anti-reprovação

  • Razão social no Business Portfolio idêntica, caractere por caractere, à do Cartão CNPJ (inclusive LTDA/ME). Divergência de nome é a causa nº 1 de reprovação.
  • Endereço e telefone do portfólio iguais aos do CNPJ na Receita. Atualize o portfólio ANTES de iniciar.
  • Site público com razão social + CNPJ visíveis (rodapé) — feito (commit 9df78d2).
  • Domínio verificado no Business Manager (meta tag) — feito (commit bddf0e2).
  • Documentos em mãos (PDF/foto nítida): Cartão CNPJ (comprovante de inscrição — emitir na hora no site da Receita), e como reserva: contrato social OU conta de consumo/fatura recente com razão social + endereço.
  • E-mail de confirmação: a Meta prefere e-mail no domínio do site da empresa (ex.: contato@<dominio-do-minhaagenda>). Se não existir, crie um alias antes — confirmar por e-mail genérico (gmail etc.) enfraquece o caso; há alternativa por telefone, mas o e-mail do domínio é o caminho liso.

Passo a passo

  • Abrir business.facebook.com → Configurações → Central de Segurança (Security Center) → cartão Verificação do negócio → Iniciar verificação. Atalho equivalente: App Dashboard → Configurações → Básico → seção Verificação → Start Verification.
  • Confirmar/editar os dados legais da empresa (razão social, endereço, telefone, site).
  • Selecionar o método de confirmação de contato (e-mail do domínio ▸ preferido; telefone como alternativa) e inserir o código recebido.
  • Upload do(s) documento(s) quando solicitado (Cartão CNPJ primeiro).
  • Aguardar. Acompanhe em Security Center → Verificação — o status muda para Em análise e depois Verificado. Chega e-mail também. selo “Verificado” no Security Center do portfólio.
Se reprovar A Meta informa o motivo (genérico). Ordem de suspeita: (1) nome divergente → corrigir portfólio e reenviar com Cartão CNPJ recém-emitido; (2) endereço → anexar conta de consumo com o endereço do CNPJ; (3) site “não relacionado” → conferir se o rodapé com CNPJ está na home e se o domínio verificado é o mesmo cadastrado no portfólio. Pode reenviar imediatamente; não há penalidade por tentativa.

§4 · FASE 3 — App Review / Acesso Avançado O GATE MAIS CHATO

Objetivo: Advanced Access em whatsapp_business_messaging (enviar/receber pelas WABAs de clientes) e whatsapp_business_management (gerenciar as WABAs deles). Sem isso, o Embedded Signup só funciona para contas com papel no app. Se o fluxo pedir business_management, solicite também com a mesma justificativa.

Onde

App Dashboard → App Review → Permissões e recursos → buscar cada permissão → Request Advanced Access → preencher a submissão única.

O que preparar (checklist da submissão)

  • Descrição do caso de uso (use e adapte): “MinhaAgenda is a SaaS scheduling platform for beauty salons in Brazil. Salon owners connect their own WhatsApp Business number via Embedded Signup. Our platform (1) receives customer messages via webhooks and lets an AI assistant + salon staff reply (whatsapp_business_messaging), and (2) manages the customer's WABA connection, phone number registration and message templates on their behalf (whatsapp_business_management). Messaging is customer-service oriented: booking, rescheduling and appointment reminders.”
  • Screencast (o item que mais reprova) — roteiro shot-a-shot:
    1. Login no painel MinhaAgenda (conta demo, dados fictícios).
    2. Navegar até Agentes → Conectar WhatsApp.
    3. Clicar no botão → popup do Embedded Signup da Meta abre (gravar o popup INTEIRO, incluindo o login FB e a seleção/criação de WABA).
    4. Concluir o fluxo → painel mostra “número conectado”.
    5. Enviar mensagem de um celular para o número → mostrar a mensagem chegando no painel e a resposta saindo.
    Grave em dev mode com um usuário que tenha papel no app (Administrador/Desenvolvedor/Testador — adicione em Funções do app). Legendas ou narração em inglês aumentam a taxa de aprovação. Nada de dados reais de clientes na tela.
  • Instruções de teste para o revisor: URL do painel + credenciais de uma conta demo funcional (salão sandbox com agente ativo). O revisor PRECISA conseguir reproduzir o caminho do vídeo.
  • Justificativa individual por permissão (2–3 frases cada, derivadas do caso de uso acima).
  • Conferir que a verificação do negócio (§2) já está concluída — submissão com portfólio não-verificado é reprovação automática.

Depois de submeter

  • Prazo típico: poucos dias a ~2 semanas. Status em App Review → Solicitações; resposta também por e-mail.
  • Se aprovar: as permissões aparecem como Advanced Access em Permissões e recursos. Agora sim: alternar o app para Live. as 2 permissões com “Acesso avançado” + app em modo Live.
  • Se reprovar: ler o feedback, corrigir SÓ o apontado e resubmeter (sem limite prático de tentativas; cada rodada custa dias — capriche na primeira).
Top 3 motivos de reprovação (e a vacina) (1) Vídeo não mostra o fluxo de ponta a ponta → grave do login ao “conectado”, sem cortes no popup. (2) Revisor não conseguiu testar → conta demo quebrada/expirada; teste você mesmo em aba anônima antes de submeter. (3) “Permissão não utilizada” → a justificativa não conecta a permissão ao que aparece no vídeo; cite a tela exata onde cada permissão age.

§5 · FASE 4 — Tech Provider, limites e Solution ID AUTOMÁTICO

  • Não existe botão “virar Tech Provider”. O status decorre de: portfólio verificado (§2) + acesso avançado (§4) + access verification quando exigida. Confira em WhatsApp Manager → Visão geral de parceiro (Partner overview).
  • Limite de onboarding: 10 clientes novos por janela móvel de 7 dias por padrão → sobe automaticamente para 200/7d ao concluir verificação + review. Acima disso: Meta Business Partner ou ticket no Direct Support. Para o estágio atual, 200/semana é mais que suficiente.
  • Solution ID — esclarecimento importante: NEXT_PUBLIC_META_SOLUTION_ID é opcional e o componente já o trata assim. Solution/Partner Solution só existe se vocês fecharem parceria formal com um Solution Partner (billing centralizado pela linha de crédito dele). No modelo escolhido (direto na Meta, cliente paga a própria conversa), não crie solution nenhuma — deixe a env vazia. Registro na memória do projeto de que isso não é pendência.
  • Consequência do modelo standalone: cada salão onboardado precisará adicionar forma de pagamento no WhatsApp Manager da própria WABA apenas para mensagens pagas (templates proativos). O fluxo reativo (janela de serviço 24h) é gratuito e funciona sem cartão.

§9 · FASE 8 — Multi-tenant de verdade: o gap de token por salão CÓDIGO

O gap, sem eufemismo Hoje connectWhatsAppCloud (apps/web/app/actions/whatsapp-cloud.ts) persiste phone_number_id/waba_id e o envio usa o token único da plataforma (WHATSAPP_CLOUD_TOKEN, System User do SEU portfólio). Isso funciona para números dentro do portfólio de vocês (piloto Spettacolo) — mas não alcança a WABA de um salão terceiro onboardado via Embedded Signup. Para o SaaS, o onboarding precisa trocar o code do ES por um token do cliente.
Fig. 3 — Onboarding server-side por salão. Hoje o código faz só o trecho ① (persistência); ②–⑥ são o trabalho novo.
  • Frontend: no retorno do ES, capturar também o code (resposta do FB.login) e enviá-lo à action junto com os IDs.
  • Server: trocar code → business token (endpoint ② — usa META_APP_SECRET server-side; nunca NEXT_PUBLIC).
  • Armazenar o token cifrado, por salão — mesmo padrão/mesa de segurança dos tokens OAuth do Google em salon_integrations (RLS já protege a tabela; token de WhatsApp entra na mesma classe de segredo).
  • ④ inscrever o app na WABA do cliente; ⑤ registrar o número (PIN de 6 dígitos = habilita a criptografia/registro Cloud); ⑥ smoke test.
  • Roteamento de envio: CloudProvider passa a resolver token por salão (fallback para o token da plataforma quando o número é do portfólio próprio — caso Spettacolo).
  • UX pós-conexão: instruir o dono a adicionar cartão no WhatsApp Manager quando for ativar lembretes/campanhas (reativo funciona sem).
Quando fazer Não bloqueia o go-live do Spettacolo (número no portfólio próprio, token da plataforma). Bloqueia o primeiro salão terceiro. Janela ideal: enquanto o App Review (§4) está na fila da Meta.
